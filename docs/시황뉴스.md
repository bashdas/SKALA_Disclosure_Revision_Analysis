# 제목 기반 시황 수집과 분석

## 현재 운영 상태와 이용 조건

2026년 10월 23일 사용자의 명시적인 활성화 요청으로 실제 수집과 제목 분류 및 뉴스 분석을 켰습니다. 발급받은 NAVER API HUB 키를 비공개 환경 파일과 External MCP 컨테이너에 반영했습니다. 실제 API 응답은 HTTP 200이며 제목과 링크 및 발행 시각을 확인했습니다.

별도 이용 계약은 확보하지 않았습니다. NEWS_USAGE_AUTHORIZATION의 현재 운영값 USER_REQUEST_20261023_NOT_A_NAVER_LICENSE는 사용자의 실행 지시를 기록하며 네이버의 이용 허락을 뜻하지 않습니다. 이 값의 존재를 검사하는 기존 코드는 운영자의 활성화 기록으로 작동합니다. 공개 이용 조건의 AI 입력과 보존 제한은 별도로 남아 있습니다. [공식 약관](https://developers.naver.com/products/terms/)

공식 API를 사용합니다. 신규 신청의 기본 공급자는 NAVER API HUB이며 NAVER_API_PROVIDER=hub로 설정합니다. 기존 유예 키가 있는 경우 legacy를 선택할 수 있습니다. NAVER_CLIENT_ID와 NAVER_CLIENT_SECRET은 비공개 환경 파일 또는 실행 환경에서 전달합니다. 키를 로그에 기록하지 않습니다. HTML 수집과 기사 본문 및 언론사 링크의 추가 크롤링은 실행하지 않습니다. [공식 이관 가이드](https://guide.ncloud-docs.com/docs/apihub-migration)

API HUB의 현재 안내는 검색 전체를 월 775,000회, 키당 최대 50 RPS로 제한합니다. 구 개발자센터 가이드는 일 25,000회를 안내합니다. 이 서비스는 자체 한도를 하루 6,000회로 더 낮게 설정하고 외부 클라이언트의 요청 시작을 초당 최대 20회로 제한합니다. 같은 키를 다른 서비스에서 사용한 양까지 알 수 없으므로 공급자의 429와 인증 오류를 기록합니다. 호출 한도 설정은 허용량을 늘리는 수단이 아닙니다. [API HUB 한도](https://guide.ncloud-docs.com/docs/apihub-overview), [구 뉴스 API](https://developers.naver.com/docs/serviceapi/search/news/news.md)

## 처리 구조

기존 External MCP가 공식 검색 API의 페이지를 반환합니다. RAG MCP의 백그라운드 수집 작업이 조회 범위와 호출 예산을 관리하고 같은 PostgreSQL의 rag 스키마에 적재합니다. 별도 DB나 서비스, 호스트 cron은 추가하지 않았습니다. 기존 RabbitMQ 분석 큐는 사용자 분석 전용으로 유지합니다. 뉴스 작업의 실행 간격과 여러 회사의 공유 수집은 이미 있는 RAG MCP 수명주기와 PostgreSQL 실행 잠금으로 처리합니다.

흐름은 수집, 제목과 URL 정규화, PENDING 최소 적재, 제한된 병렬 분류, 메타데이터 갱신, 검색 및 선택적 제목 임베딩 순서입니다. 페이지별로 최소 기록을 먼저 커밋해 모델 장애와 프로세스 종료 후에도 재처리할 수 있습니다. PENDING, FAILED, UNRESOLVED는 확정 태그 검색에서 제외합니다. 본문과 검색 API의 description은 저장하지 않습니다.

즐겨찾기는 업무 DB에서 활성 사용자의 기업을 모으고 회사 코드로 합칩니다. 기존 즐겨찾기 등록 API는 외부 회사 목록에서 확인한 이름을 저장합니다. 공개 회사명과 운영자가 확인한 별칭만 검색하며 메모, 사용자 ID와 즐겨찾기 사용자 신원을 전달하지 않습니다. 한국어 검색 범위이므로 해외 기업과 한글 별칭이 없는 기업은 누락될 수 있습니다.

단독으로 식별되는 정식 기업명은 사전 일치로 직접 연결합니다. 복수 기업과 짧은 별칭, 모호한 제목, 산업 및 거시 뉴스는 모델로 분류합니다. 모델에는 서버의 기업 후보 식별자만 제공하며 알 수 없는 코드를 거부합니다. 짧은 별칭만 있거나 계열사 이름의 접두사만 일치하면 확정을 보류합니다. 기업은 직접 언급 기업만 연결합니다. 금리 뉴스의 잠재 영향으로 모든 기업을 연결하지 않습니다. 신뢰도는 모델의 주관적 평가이며 검증된 확률이 아닙니다. 모델이 분류 범위와 기업 코드를 서로 맞지 않게 반환하면 해당 기사만 UNRESOLVED로 남깁니다. 같은 배치의 정상 기사 처리는 계속합니다. 후보 목록 밖의 기업 코드도 해당 기사에서 연결을 거부하고 미확정 사유로 기록합니다. 다른 기사의 분류 결과는 보존합니다.

## 주기, 재개와 예산

기본 실행 간격은 3,600초입니다. 수집은 웹 요청과 사용자 분석에서 독립적으로 실행됩니다. 이전 작업이 잠금을 유지하면 다음 작업은 생략합니다. 시작 시각을 DB에 보존하므로 프로세스 재시작으로 같은 시간대 작업을 중복 실행하지 않습니다. 중단된 수집의 최소 적재 행은 남고 다음 처리에서 분류를 재개합니다. 실행 로그는 기사와 별도의 표에 남깁니다.

처음에는 최근 24시간을 조회하고 이후 검색어별 마지막 성공 지점부터 2시간을 겹쳐 조회합니다. 실패 후 재개는 최대 72시간으로 제한합니다. 페이지 제한에 걸리면 성공 지점을 앞당기지 않고 조회하지 못한 범위를 남깁니다. API가 전체 기간 검색을 보장하지 않고 시작 위치에도 상한이 있으므로, 최근 기사만으로 페이지를 소진하면 이전 구간이 계속 확보되지 않을 수 있습니다. 이 경우 PAGE_LIMIT_REACHED와 범위를 운영 기록에서 확인합니다.

한 회차의 공통 주제 예산은 30회, 회사 검색 예산은 120회입니다. 공통 시황부터 조회하고 회사 쪽의 미사용 예산을 넘겨 공통 예산을 소진하지 않습니다. 회사가 많으면 마지막 조회 시각이 오래된 검색어부터 처리합니다. 검색어별 최대 3페이지, 페이지당 100개입니다. 일일 사용량은 DB에서 호출 전에 증가시켜 재시작으로 한도가 초기화되지 않게 했습니다.

분류 기본값은 동시 2배치, 배치당 10제목, 회차당 최대 20배치입니다. 현재 로컬 운영 설정은 사용자 요청으로 배치당 20제목과 최대 100배치(대기 항목 2,000건), 회차별 예약 예산 500,000토큰으로 늘렸습니다. 동시 호출 2개와 요청당 30초, 재시도 제한은 유지합니다. 이는 기본값 64,000토큰과 구분되는 backend/.env 운영 설정입니다. 최대 출력 4,000토큰, 요청당 30초, 추가 재시도 1회와 기사당 누적 처리 3회 한도를 둡니다. 회차별 입력과 출력 예약 상한은 64,000토큰이며 보수적인 문자 수 기반 입력 상한을 더해 예약합니다. 예산이 남지 않으면 최소 적재 행을 대기 상태로 보존합니다. 수동 retry는 만료 전 실패 항목의 실행 대기와 횟수 제한을 명시적으로 다시 시도할 수 있게 합니다.

정기 뉴스 작업은 사용자 분석의 모델 예산을 사용하지 않습니다. 사용자 분석은 기존 120초, 보고서 시간 30초 예약, 분석 전 64,000토큰과 10턴, 전체 80,000토큰과 12턴을 유지했습니다. 각 관점의 입력 상한은 8,000토큰으로 맞췄습니다. 실제 뉴스 메타데이터가 포함된 재무 및 계약 관점의 고정 입력이 이전 6,000토큰 한도를 넘어 모델 호출 전 차단되는 사례를 재현했습니다. 전체 64,000토큰 분석 한도와 보고서용 전체 80,000토큰 한도는 유지했습니다. 이번 변경에서 별도 기사 선택 모델 호출을 제거했습니다. 네 관점이 모두 추가 조회를 반복해 한도에 닿는 경우에도 최종 보고서와 출력 검사를 수행하는 회귀 검사가 통과했습니다.

## 데이터와 보존

market_news에는 내부 ID, 원래 제목, 정규화 제목, 검색 결과 및 원문 링크, 발행과 최초 및 마지막 수집 시각, 검색어, 직접 관련 기업, 분류 범위와 산업 및 시황 태그, 처리 상태와 방법, 모델 및 정책 버전, 불확실성, 주관적 신뢰도, 중요도와 이유, 만료 시각, 시도 횟수와 오류, 색인 상태를 보존합니다. 제목 임베딩은 선택 사항이며 기본값은 꺼져 있습니다. 활성화하면 새 제목이나 실제로 바뀐 제목만 생성하고 분류 정책 변경만으로 같은 제목을 다시 임베딩하지 않습니다.

일반 뉴스는 발행 후 7일, 중요 뉴스는 최대 30일, 미확정 및 분류 실패는 최대 48시간을 기본값으로 정했습니다. 최소 적재 대기는 최초 확보 후 48시간으로 두어 늦게 발견된 기사를 분류할 기회를 남깁니다. 확정 분류 후에는 발행 시각과 최초 수집 시각 중 이른 시각을 기준으로 보존 기한을 고정합니다. 재수집으로 만료일을 연장하지 않습니다. 중요 기사도 설정 상한을 넘겨 무기한 보존하지 않습니다. 사용자 요청으로 이 운영값을 적용했습니다. 별도 이용 허용 계약은 확보하지 않았습니다.

활성 뉴스는 기본 50,000행, 행 크기 합계 128 MiB까지 관리합니다. 페이지 적재 후와 회차 종료 시 초과분을 정리합니다. 만료된 행, 실패 및 미확정, 일반 뉴스의 오래된 순서로 정리하고 중요 뉴스는 뒤에 둡니다. 이 용량은 활성 행과 벡터의 논리 크기입니다. PostgreSQL의 물리 파일, 색인과 WAL 용량에는 별도 디스크 감시와 VACUUM 운영이 필요합니다.

태그와 벡터는 기사와 같은 행에 있어 삭제가 함께 반영됩니다. 활성 뉴스의 별도 파일 캐시는 없습니다. 실행 로그와 검색 상태 및 사용량은 기본 14일을 보존합니다. 만료 정리는 수집 활성 여부와 별도로 주기적으로 실행합니다. 기존 0002 방식의 행은 LEGACY로 표시하고 새 분류 검색에서 제외하며 이전 원문과 보고서를 덮어쓰지 않습니다.

보고서가 실제 인용한 기사 제목, URL, 발행 시각과 분류 당시 메타데이터는 report_json.news_snapshots에 복사하고 사용한 제목 인용도 기존 출처에 보존합니다. 활성 뉴스와의 삭제 종속 관계를 두지 않았습니다. 별도 이용 조건에 스냅샷 보존도 허용되는지 확인해야 실제 데이터로 사용할 수 있습니다.

## 검색과 시황 관점

기존 메모 및 공시의 search_evidence 계약을 유지하고 search_market_news를 별도 도구로 사용합니다. 새 자료를 기존 메모 문서 유형에 섞지 않고 뉴스만의 시간, 태그와 제한을 반환하기 위한 선택입니다. 작업 ID로 Business MCP의 실제 대상 기업과 요청 생성 시각을 확인합니다. 모델이 임의로 대상 기업 코드를 지정할 수 없습니다.

입력은 task_id, query, top_k와 선택적 as_of, days, scopes, topics입니다. COMPANY, INDUSTRY, MACRO 범위와 주제 필터, 제목 단어 일치, 최신성을 합칩니다. 선택적 제목 벡터를 추가할 수 있으며 임베딩 실패 시 메타데이터 및 단어 검색으로 이어갑니다. 산업 매핑은 NEWS_COMPANY_INDUSTRIES의 확인된 회사 사전을 사용하고 요청한 주제와 연결되는 산업 뉴스도 찾을 수 있습니다. 공통 시황과 개별 기업의 영향 연결은 분석 모델이 별도로 평가합니다.

기본 시각은 작업 요청 생성 시각이며 이를 넘는 시각을 요청해도 서버에서 제한합니다. 과거 as_of에는 당시 발행됐고 시스템이 수집과 분류까지 완료한 자료만 조회합니다. 날짜만 있으면 한국 시간 그날 마지막 시각으로 해석하되 요청 시각을 넘지 않습니다. 모든 저장 시각은 시간대가 있는 값입니다. 자료 수집 당시의 실제 시각을 기록하고 수집 시작 시각으로 소급하지 않습니다. 보관 기간이 지난 과거 자료와 변경된 예전 제목을 완전히 복원하는 기능은 제공하지 않습니다.

시황 관점은 정책과 산업 수요, 원자재와 고객 및 공급망 같은 메모 가정의 재점검이 필요할 때 기본 모델이 선택합니다. 네 관점을 일괄 실행하지 않습니다. 시황은 최근 보도 사건과 점검 질문, 외부환경 관점은 환율과 금리 및 헤지 노출의 전달 경로를 담당하도록 질문과 프롬프트를 나눴습니다. 같은 조회는 기존 공유 조회 캐시를 사용하며 보고서 모델에는 반복 서술을 줄이도록 지시합니다.

제목에서 확인 가능한 보도 내용, 메모 및 공시와의 연결, 조건부 영향과 추가 질문, 제목만으로 모르는 사항을 구분합니다. 기사 본문에 있을 조건과 숫자를 만들지 않습니다. search_market_news는 수집 DB만 읽습니다. 호환용 read_market_news도 저장 제목만 반환하고 read_naver_news_article은 NEWS_BODY_DISABLED를 반환합니다.

자료 없음, 미수집, 최신성 초과, 검색 실패, 주장 근거 부족, 출처 연결 실패와 출력 검사 실패를 서로 다른 코드와 제한 사유로 남깁니다. 출력 검사 실패를 실제 근거 부족으로 단정하지 않습니다. 보고서에는 기준 시각과 조회 기간 및 제목 한계를 기록하고 실제 사용한 추가 과거 조회의 범위도 보존합니다.

## 운영 명령

아래 명령은 backend 폴더에서 실행합니다. 현재 collect와 retry는 실제 공식 API와 분류 모델을 사용합니다. 명령 실행 시 호출량과 모델 비용이 발생할 수 있습니다.

```bash
docker compose -p disclosure-web exec rag-mcp python -B -m app.news_admin status
docker compose -p disclosure-web exec rag-mcp python -B -m app.news_admin collect
docker compose -p disclosure-web exec rag-mcp python -B -m app.news_admin retry
docker compose -p disclosure-web exec rag-mcp python -B -m app.news_admin cleanup
docker compose -p disclosure-web exec rag-mcp python -B -m app.news_admin cleanup --apply
```

cleanup의 기본값은 미리보기이며 삭제 예정 수와 남을 행 수 및 논리 용량을 보여줍니다. --apply에서 실제 정리를 실행합니다. 모든 명령은 정기 작업과 같은 DB 잠금을 사용합니다. DB 마이그레이션은 RAG 0003_news_pipeline을 추가했습니다. DB에는 기존 Core의 네 관점 제약을 유지합니다.

환경변수와 기본값은 backend/.env.example과 docker-compose.yml에 있습니다. 주기는 NEWS_COLLECTION_INTERVAL_SECONDS, 검색 주제는 NEWS_TOPICS의 JSON 목록, 확인된 별칭과 산업 매핑은 NEWS_COMPANY_ALIASES 및 NEWS_COMPANY_INDUSTRIES의 JSON 사전입니다. 보존과 용량, API 호출과 모델 예산은 각각 NEWS_RETENTION_DAYS, NEWS_IMPORTANT_RETENTION_DAYS, NEWS_UNRESOLVED_RETENTION_HOURS, NEWS_MAX_ARTICLES, NEWS_MAX_STORAGE_BYTES 및 NEWS_*_BUDGET 설정을 사용합니다. 실험용 SYNTHETIC_TEST_ONLY 값은 합성 테스트에서만 사용합니다.

검증 결과와 미확인 범위는 [제목 시황 검증](검증/시황제목_20261023/결과.md)에 기록했습니다. 과거 본문 수집 방식의 기록은 당시 상태를 보여주는 기존 검증 폴더에 보존했습니다.
