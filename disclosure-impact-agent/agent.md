# Git 컨벤션과 작업 문서화

이 문서는 이 저장소에서 앞으로 수행하는 작업의 기준입니다. 기존 이력과 브랜치 이름은 유지합니다. 문서에 없는 팀 합의가 있으면 확인한 뒤 반영합니다.

## 작업 시작

현재 브랜치와 변경 파일을 먼저 확인합니다. 다른 사람이 작성한 변경은 보존합니다. 로컬 변경이 있으면 처리 방법을 확인한 뒤 브랜치를 전환하거나 원격 변경을 반영합니다.

```bash
git status
git fetch origin
git switch main
git pull --ff-only origin main
```

명령이 실패하면 원인을 확인하고 해결한 뒤 다음 단계로 진행합니다. 충돌이나 분기 이력을 강제 초기화로 덮어쓰지 않습니다.

## 이슈

새 작업은 GitHub 이슈로 목적과 완료 조건을 정한 뒤 시작합니다. 이슈 하나는 검토 가능한 하나의 작업을 다룹니다. 범위가 커지면 하위 작업을 별도 이슈로 나누고 서로 연결합니다.

제목은 `[종류] 작업 내용` 형식을 사용합니다. 예시는 `[feat] 공시 정정 비교 기능 추가`, `[fix] 계약 금액 누락 시 오류 수정`입니다. 종류는 아래 커밋 종류와 동일하게 사용합니다.

담당자는 실제 작업자 한 명을 지정합니다. 라벨은 저장소에 등록된 항목 중 작업 종류와 맞는 것을 사용합니다. 마일스톤은 팀에서 정한 일정이 있을 때 지정합니다. 완료 조건은 확인할 수 있는 체크리스트로 작성합니다.

```markdown
## 배경과 목적
현재 문제와 필요한 결과를 적습니다.

## 작업 범위
수정할 대상과 이번 작업에서 다룰 범위를 적습니다.

## 완료 조건
- [ ] 요구한 동작 또는 문서가 반영됐습니다.
- [ ] 확인 절차와 결과를 기록했습니다.

## 참고 자료
관련 이슈, 문서, 재현 자료를 연결합니다.
```

오류 이슈에는 재현 순서, 실행 환경, 기대 결과와 실제 결과를 추가합니다. 진행 중 막힌 일이 생기면 원인과 필요한 조치를 댓글에 기록합니다. PR 병합 후 완료 조건을 확인하고 이슈를 닫습니다. 취소하거나 중복으로 닫을 때는 이유와 관련 이슈를 남깁니다.

## 브랜치 이름과 생성

`main`은 팀에서 함께 사용할 기준 브랜치로 유지합니다. 새 작업은 최신 `main`에서 작업 브랜치를 만들고 PR(Pull Request, 변경 검토 요청)로 병합합니다. 기존 개인 브랜치는 계속 사용할 수 있습니다.

새 브랜치 이름은 `종류/이슈번호-짧은-설명` 형식을 사용합니다. 예시는 `feat/12-disclosure-parser`, `fix/23-date-validation`, `docs/31-git-convention`입니다. 예시 번호는 실제 이슈 번호로 바꿉니다.

종류는 아래 커밋 종류를 사용합니다. 설명에는 영문 소문자와 숫자를 쓰고 단어는 하이픈으로 구분합니다. 공백과 개인 이름은 넣지 않습니다. 이슈 하나에 작업 브랜치 하나를 사용하고 관련 없는 변경은 별도 이슈와 브랜치로 나눕니다.

```bash
git switch -c docs/31-git-convention
```

공유 브랜치의 강제 푸시와 이력 재작성, 브랜치 삭제는 명시적인 요청이 있을 때만 수행합니다.

`main`에 직접 커밋하거나 푸시하지 않습니다. 긴급 수정도 `fix/이슈번호-설명` 브랜치에서 PR로 진행합니다. 병합된 브랜치는 재사용하지 않고 다음 이슈에 맞는 새 브랜치를 만듭니다.

## 커밋

커밋 제목은 `종류: 변경 내용` 형식으로 작성합니다. 제목에는 실제 바뀐 내용을 구체적으로 적습니다. 관련 없는 변경은 커밋을 나눕니다.

| 종류 | 사용 기준 |
| --- | --- |
| `feat` | 기능을 추가합니다. |
| `fix` | 잘못된 동작을 수정합니다. |
| `docs` | 문서를 작성하거나 수정합니다. |
| `refactor` | 외부 동작을 유지하며 코드를 정리합니다. |
| `test` | 검증 코드를 추가하거나 수정합니다. |
| `chore` | 의존성, 설정, 관리 작업을 변경합니다. |

예시는 `feat: 공시 정정 전후 비교 추가`, `fix: 누락된 계약 금액 처리`, `docs: 작업 기록 작성 기준 추가`입니다. 이유나 주의점이 제목만으로 드러나지 않으면 커밋 본문에 적습니다.

관련 이슈는 커밋 본문에 `Refs #31`처럼 연결합니다. 커밋 작성자는 실제 작업자의 이름과 이메일을 사용합니다. 다른 팀원의 작성자 정보를 사용하지 않습니다.

변경 파일을 확인하고 필요한 파일만 명시적으로 스테이징합니다. 커밋 전에 스테이징된 차이를 확인합니다. 비밀키, 인증 정보, 개인정보와 실행 캐시는 올리지 않습니다.

```bash
git diff
git add agent.md
git diff --cached
git commit -m "docs: Git 컨벤션과 작업 문서화 기준 추가"
```

## PR 작성

PR 제목은 `종류: 변경 내용 (#이슈번호)` 형식을 사용합니다. 예시는 `docs: Git 협업 규칙 추가 (#31)`입니다. 병합 대상은 `main`, 작업 브랜치는 해당 이슈의 브랜치로 지정합니다. PR 하나는 연결된 이슈의 범위를 다룹니다.

작성 중이거나 검증이 끝나지 않은 PR은 Draft로 엽니다. 검토 준비가 끝나면 일반 PR로 전환하고 작성자 외 팀원 한 명 이상에게 리뷰를 요청합니다. 담당자는 PR 작성자로 지정합니다.

본문에는 해결하려는 문제, 변경된 동작, 실제 수행한 검증과 결과를 적습니다. 남은 문제나 실행하지 못한 검증은 이유와 함께 밝힙니다. 기능을 일부만 반영한 PR은 관련 이슈를 `Refs #31`로 연결합니다. 이슈의 완료 조건을 모두 충족하는 PR은 `Closes #31`로 연결합니다.

```markdown
## 관련 이슈
Closes #31

## 변경 목적
해결하려는 문제를 적습니다.

## 변경 내용
주요 변경과 사용자에게 미치는 영향을 적습니다.

## 검증 결과
실행한 명령, 확인한 동작과 실제 결과를 적습니다.

## 검토 요청과 남은 작업
집중해서 봐야 할 부분과 미해결 사항을 적습니다.

## 확인 항목
- [ ] 이슈의 작업 범위를 확인했습니다.
- [ ] 변경 내용을 검증하고 결과를 기록했습니다.
- [ ] 필요한 문서를 갱신했습니다.
- [ ] 인증 정보와 불필요한 생성 파일을 제외했습니다.
```

## 검증과 리뷰, 병합

코드 변경은 바뀐 동작을 확인할 수 있는 검증을 수행합니다. 문서 변경은 내용과 명령 예시, 경로를 확인하고 `git diff --check`로 공백 오류를 검사합니다. 검증하지 않은 내용을 통과했다고 적지 않습니다.

푸시 전에는 현재 브랜치와 커밋 내용을 확인합니다. 작업 브랜치를 원격에 올린 뒤 PR을 생성합니다. 병합 전에는 팀 검토를 받습니다.

```bash
git status
git log -1 --oneline
git push -u origin HEAD
```

리뷰 의견에는 파일과 위치, 문제의 근거, 필요한 변경을 적습니다. 작성자는 수정 내용이나 적용하지 않은 이유를 답변합니다. 수정 후에는 관련 검증을 다시 수행하고 리뷰어에게 재확인을 요청합니다.

작성자 외 팀원 한 명 이상의 승인, 미해결 리뷰 의견 해소, 충돌 해결을 병합 조건으로 합니다. 자동 검사가 구성돼 있으면 해당 검사도 통과해야 합니다. 자동 검사가 없으면 수동 검증 결과를 PR 본문에 남깁니다.

충돌은 작업 브랜치에서 최신 `main`을 병합해 해결합니다. 다른 사람의 변경 의도를 확인하고 충돌 해결 후 다시 검증합니다. 공유한 브랜치의 이력을 강제로 바꾸지 않습니다.

```bash
git fetch origin
git merge origin/main
```

병합 방식은 Squash and merge를 기본으로 합니다. 여러 작업 커밋을 하나로 합치는 방식이며, 병합 커밋 제목은 PR 제목 형식을 따릅니다. 저장소 설정에서 이 방식을 사용할 수 없으면 팀과 병합 방식을 확인합니다. 병합 후 관련 이슈의 완료 상태를 확인하고 로컬 `main`을 `git pull --ff-only origin main`으로 갱신합니다. 브랜치 정리는 명시적인 요청을 받은 뒤 수행합니다.

## 작업 문서화

모든 에이전트는 작업을 시작하기 전에 이 문서를 읽고 자신이 지원하는 팀원의 기록 문서를 확인합니다. 담당자별 기록 위치는 다음과 같습니다.

| 담당자 | 기록 문서 |
| --- | --- |
| 상욱 | [상욱 작업 기록](docs/상욱.md) |
| 건민 | [건민 작업 기록](docs/건민.md) |
| 다솔 | [다솔 작업 기록](docs/다솔.md) |
| 경은 | [경은 작업 기록](docs/경은.md) |
| 승호 | [승호 작업 기록](docs/승호.md) |
| 동민 | [동민 작업 기록](docs/동민.md) |

에이전트는 자신을 사용하는 팀원의 문서에 실제 수행한 작업을 기록합니다. 담당자가 불명확하면 사용자에게 확인합니다. 여러 에이전트가 같은 담당자를 지원하면 에이전트 이름과 작업 제목으로 기록을 구분합니다. 다른 담당자의 기록을 임의로 수정하지 않습니다.

작업을 시작할 때 새 기록을 문서 끝에 추가하고 시작 시각, 요청 내용, 담당 에이전트와 작업 상태를 적습니다. 작업을 마치거나 중단할 때 종료 시각, 변경 파일과 수행 내용, 검증 결과, 트러블슈팅과 남은 작업을 갱신합니다. 커밋하는 작업에서는 해당 기록도 함께 포함합니다. PR 본문에는 담당자 기록의 해당 항목을 연결합니다.

시각은 실제 시계를 확인해 한국 시간(Asia/Seoul) 기준 `YYYY.MM.DD HH:mm KST` 형식으로 적습니다. 과거 작업 시간을 추정해서 채우지 않습니다. 상태는 `진행 중`, `완료`, `중단` 중 하나로 적고, 중단한 경우 이유와 재개 조건을 남깁니다. 기존 기록은 보존하고 새 작업을 이어서 추가합니다.

트러블슈팅에는 증상과 재현 조건, 원인, 시도한 조치, 해결 여부와 재검증 결과를 적습니다. 확인하지 못한 원인은 추정임을 밝히고 실패한 시도도 남깁니다. 문제가 없으면 `발생한 문제는 없습니다.`라고 적습니다. 검증을 수행하지 않았으면 그 이유를 적고 완료 여부와 구분합니다.

기능 구현, 오류 수정과 설정 변경을 마칠 때는 PR 본문에 작업 기록을 남깁니다. 재현 방법이나 설계 근거처럼 다음 작업에도 필요한 내용은 관련 문서에 함께 기록합니다. 이미 관련 문서가 있으면 그 문서를 갱신합니다.

요구사항과 구현 결과를 구분합니다. 완료한 작업은 과거형으로, 남은 작업은 미완료 상태로 적습니다. 검증 기록에는 명령이나 확인 절차와 관찰한 결과를 함께 적습니다. 로그와 화면 이미지에서는 인증 정보와 개인정보를 가립니다.

담당자 문서의 새 기록에는 다음 양식을 사용합니다. PR 본문에는 관련 기록을 연결하고 핵심 결과를 요약합니다.

```markdown
## YYYY.MM.DD HH:mm KST 작업 제목

시작 시각: YYYY.MM.DD HH:mm KST
종료 시각: 진행 중
작성자: 이름
에이전트: 사용한 에이전트 이름
상태: 진행 중
브랜치: 작업 브랜치 이름
관련 이슈와 PR: 연결 주소 또는 미생성

### 목적
어떤 문제를 해결하려고 했는지 적습니다.

### 변경 내용
변경한 파일과 동작, 선택한 방법의 이유를 적습니다.

### 검증 결과
수행한 명령이나 확인 절차와 실제 결과를 적습니다.
수행하지 못한 검증은 이유를 적습니다.

### 트러블슈팅
증상과 재현 조건, 원인, 시도한 조치, 해결 여부와 재검증 결과를 적습니다.
문제가 없으면 발생한 문제는 없다고 적습니다.

### 남은 작업
미해결 문제와 다음에 확인할 내용을 적습니다.
없으면 없다고 적습니다.
```

커밋과 푸시는 사용자가 요청하거나 해당 작업 범위에 포함됐을 때 수행합니다. 결과를 보고할 때는 로컬 작성, 커밋, 원격 반영 중 어디까지 끝났는지 구분합니다.
